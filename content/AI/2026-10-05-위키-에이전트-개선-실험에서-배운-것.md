회사에서 프로젝트 수행 자료(주간보고, 월간 메일, PMO 점검 보고 등)를 올리면 에이전트가 프로젝트 위키를 써 주는 기능을 만들고 있다. 진척, 인력, 원가, 요구사항, 리스크 같은 주제 페이지가 있고, 모든 문장에는 원문 블록을 가리키는 근거 표기가 붙는다.

```text
- 2025-11-21 기준 전체 WBS 실적 62.55%, 계획 65.03%, 달성률 96.19% [근거: /parsed/.../59주차 점검 보고.md#blk-0003 "WBS 기준 62.55%"]
```

구조는 deepagents 기반이다. 부모 에이전트가 원본마다 읽기 담당(reader)을 띄우고, 결과를 모아 위키를 고치고, 화면 저장 담당들을 부른다.

문제는 위키가 얇다는 것이었다. 원본 12건에서 reader가 뽑은 사실 중 정리 페이지에 들어간 것이 11% 남짓이었다. 이걸 고치려고 같은 원본 12건을 고정해 두고 실험을 스무 번 가까이 다시 돌렸다. 아래는 그 과정에서 얻은 것들이다.

## 실험 흐름 한눈에

| 실험 | 바꾼 것 | run 시간 | 정리 페이지 근거 줄 | 인용한 원문 블록 |
| -- | -- | -- | -- | -- |
| H3 | reader가 원문을 조각내 빠짐없이 사실로 옮김 | 38분 | - | - |
| M | 사실을 위치 태그로 코드가 주제 절에 배치 | 17분 46초 | 165 | 33 |
| O | 사실을 별도 페이지로 빼고 부모가 정리 | 19분 32초 | 103 | 39 |
| P2 | 페이지마다 작성 담당(23개 동시) | 58분 32초 | 201 | 90 |
| R | 동시 6개 제한, 사실 사본 제거 | 31분 58초 | 276 | 104 |
| T3 | 주제 묶음 담당이 원문을 직접 읽고 씀 | **5분 56초** | 270 | 71 |

모두 같은 원본 12건(pptx 5, 메일 4, docx 2, pdf 1)이고 시간은 파싱을 뺀 위키 업데이트 시간이다.

## 1. 빠짐없이 뽑으니 반영률은 올랐지만 위키는 나빠졌다

처음 원인은 reader로 보였다. 큰 주간보고 하나가 10만 자쯤 되는데 reader가 원본당 사실을 20~30개만 뽑고 있었다. 그래서 원문을 블록 표식 경계로 1.6만 자씩 조각내 동시에 읽히고, 블록마다 "옮김 / 넘김 / 못 봄"을 기록하는 원장을 두었다. 사실 수는 302개에서 3,883개로 늘었다.

그런데 부모가 그 사실을 다 옮기지 못했다. 사실을 페이지에 놓는 일은 대부분 "이 사실은 진척의 마일스톤 절" 같은 분류라서, reader가 사실마다 위치 태그(`{진척/마일스톤}`)를 붙이고 코드가 그 절에 넣게 했다. 반영률은 11%에서 83%가 됐다.

숫자는 좋아졌지만 실제 페이지를 열어 보니 원본 12건만으로 정리 페이지에 사실 4,273줄이 쌓여 있었다. 사람이 읽을 수 있는 위키가 아니라 원본을 다시 쏟아 놓은 목록이었다. 반영률은 "사실이 정리 페이지에 있느냐"를 셌을 뿐 "정리가 되었느냐"를 세지 않았다.

이후로는 반영률 대신 정리 페이지의 근거 줄 수, 인용한 서로 다른 원문 블록 수, 어느 페이지에도 없는 사실 수를 함께 봤다. 그리고 핵심 수치(전체 진척률 같은 것)가 "현재 상황"에 실제로 들어갔는지를 눈으로 확인했다.

## 2. 사본은 근거 사슬에 아무것도 더하지 않는다

4,273줄 문제를 풀려고 절마다 최근 원본 3건의 사실만 남기는 상한을 넣었다. 그러자 "몇 건을 남길지 왜 코드가 정하나", "이전부터의 추이는 어떻게 보나"라는 질문이 나왔다. 둘 다 맞는 지적이었다.

다음 시도는 사실 전부를 주제별 원본 사실 페이지(`facts/progress.md`)로 빼는 것이었다. 정보는 보존됐지만 결국 이것도 reader 결과의 사본이었다. 근거 사슬은 원래 "위키 문장 → `[근거: /parsed/...]` → 원문" 이고, 원문 전체는 원본별 문서 페이지에 이미 있다. 중간에 낀 사본은 사슬에 아무것도 더하지 않으면서 게시 위키에 페이지만 늘렸다. 사본을 지우고, 나눈 사실은 그 페이지를 쓰는 담당의 입력으로만 넘겼다.

## 3. 한 명에게 몰린 일은 지시문으로 풀리지 않는다

사실 배치를 어떻게 바꿔도 부모가 쓴 근거 줄은 165, 151, 103줄 사이에서 움직였다. 부모 한 명이 모델 호출 약 100번으로 40여 쪽을 쓰고 있었기 때문이다. 지시문을 고쳐 "현재 상황을 갱신하라"고 해도 바뀌지 않았다.

페이지마다 작성 담당(topic-writer)을 두고 동시에 돌리자 근거 줄이 201, 276까지 올라갔다. deepagents 문서가 권하는 대로 부모는 지휘만 하고, 맥락이 큰 일은 서브에이전트에 나눠 맡긴 셈이다.

반대 방향도 시험했다. 부모가 쓰고 페이지마다 검토 담당이 피드백만 주는 구조(평가자-개선자)였다. 검토 23건은 동시에 금방 끝났지만, 부모가 피드백을 페이지마다 차례로 반영하느라 그 단계만 37분이 걸렸고 품질도 더 낮았다. 병목은 검토가 아니라 부모의 차례 처리였다.

## 4. 병렬 호출의 한계는 공급자 쪽에서 온다

작성 담당 23개를 한꺼번에 띄운 실험 P2는 58분이 걸렸다. 로그를 보니 담당들이 한꺼번에 시작한 직후 LLM 요청이 분당 1~10건으로 떨어졌다. 호출 하나에 입력이 4만~18만 토큰씩 몰리자 Azure OpenAI가 429도 없이 응답을 멈췄고, 클라이언트는 180초 timeout을 다 기다린 뒤 재시도하고 있었다. 출력은 몇백 토큰인데 190~217초씩 걸린 호출이 20건이었다.

429가 오면 물러섰다 다시 부르면 되지만, 응답이 그냥 멈추면 timeout까지 기다리는 시간이 그대로 전체 시간이 된다. 동시 호출 수를 6개로 묶고 담당 입력을 절반으로 줄이자 58분이 24분으로 내려왔다. 병렬화는 내 코드가 아니라 모델 배포의 처리량이 상한이다.

## 5. 같은 원본으로 단일 에이전트와 비교해 보니

여기까지 오고도 run은 20~30분이었다. 그래서 같은 원본으로 단일 에이전트(Claude, 서브에이전트 없이)에게 진척·인력·Activity 한 쪽씩 세 페이지를 쓰게 했다. 6분이 걸렸다.

| 페이지 | 위키(실험 R) 근거 줄 / 인용 블록 | 단일 에이전트 근거 줄 / 인용 블록 |
| -- | -- | -- |
| 진척 | 34 / 16 | 52 / 46 |
| 인력 | 30 / 11 | 35 / 23 |
| Activity(진척/품질) | 4 / 15 | 5 / 24 |

더 아팠던 건 내용이었다. 단일 에이전트의 진척 페이지 첫 줄은 전체 WBS 진척률이었는데, 위키의 "현재 상황"에는 그 수치가 아예 없었다. 여러 행이 같은 인용문 `"3,569"` 하나를 근거로 달고 있기도 했다. 숫자 하나만 맞으면 근거 검사를 통과하기 때문이다.

단일 에이전트가 한 일은 단순했다.

1. 짧은 메일·점검 보고는 통째로 읽고, 큰 주간보고는 진척 표·인력 표·이슈 행만 grep으로 뽑았다.
2. 읽은 내용을 한 맥락에 둔 채 바로 페이지를 썼다.
3. 인용문이 실제 블록에 있는지만 스크립트로 확인했다.

위키는 원문을 사실 3,800개로 쪼개고, 코드가 나누고, 담당이 다시 합치고, 검증 담당이 보고, 부모가 고쳤다. 단계마다 핵심이 조금씩 빠졌고, 중간 산출물을 만들었다 다시 읽는 비용이 쌓였다. 꼼꼼함을 위해 넣은 단계들이 오히려 정리를 얇게 만들고 있었다.

## 6. 최종 구조: 묶음 에이전트가 원문을 직접 읽는다

단일 에이전트처럼 일하되 대량 자료에도 버티도록 이렇게 바꿨다.

- 부모는 `eval` 한 번에 원본마다 reader(원본별 문서 페이지)와 주제 묶음마다 작성 담당을 함께 띄운다. 그다음 주간·월간 요약과 화면 저장 담당을 맡기고 끝낸다.
- 작성 담당은 11개 묶음(사업 개요, 진척·일정, 인력, 원가·규모, 요구사항·평가·PRB, 리스크 4묶음, 기타 주제, 주간·월간 요약)으로 나눴다. 각자 현재 페이지를 보고 이번 원본을 grep·read로 직접 찾아 읽어 고친다. 원문을 맥락에 통째로 싣지 않으니 원본이 수백 건이어도 같은 방식이 통한다.
- 근거 검사는 코드가 한다. 담당이 끝내려 할 때 인용문이 블록에 있는지 검사해 고칠 수 있는 것은 고치고, 남은 줄은 두 번까지 그 담당에게 돌려준다. LLM 검증 담당은 뺐다.
- 어느 묶음에도 맞지 않는 내용은 기타 주제 담당이 `topics/` 페이지로 쓴다. 실험에서는 데이터 이행, 시스템 연계 페이지가 새로 생겼다.

결과는 5분 56초, 정리 페이지 근거 줄 270, 어느 페이지에도 없는 사실 26개였다. 처음(17분 46초, 165줄)과 비교하면 시간은 3분의 1, 정리는 1.6배다.

묶음 크기도 중요했다. 처음에는 리스크 담당 하나에 Activity 16쪽을 맡겼더니 Activity 하나에 Risk case가 1행만 들어갔다. 담당 하나가 맡는 페이지를 1~4쪽으로 줄이자 나아졌다. 담당을 나누는 기준은 "동시에 몇 개까지 돌릴 수 있나"와 "한 담당이 몇 쪽까지 집중할 수 있나" 사이에서 정해진다.

## 정리: 다음에도 쓸 것들

- **지표가 좋아질 때 실제 결과를 연다.** 반영률 83%짜리 위키는 4,273줄짜리 목록이었다. 지표 하나보다 근거 줄, 인용 블록 수, 빠진 사실 수, 핵심 수치 포함 여부를 함께 본다.
- **중간 산출물과 단계는 비용이다.** 쪼개고 나누고 다시 합칠 때마다 핵심이 빠지고 시간이 든다. 같은 일을 단일 에이전트에게 시켜 보면 구조가 얼마나 무거운지 바로 보인다.
- **꼼꼼함은 코드로, 판단은 LLM에.** 인용문이 원문에 있는지는 코드가 빠르고 정확하게 본다. 무엇이 현재 유효한지, 어떤 추이인지는 LLM이 원문을 보고 판단하게 둔다.
- **병렬화의 상한은 공급자다.** 429 없이 응답이 멈추는 경우가 있고, 그러면 timeout이 곧 전체 시간이 된다. 동시 호출 수와 호출당 입력 크기를 같이 묶어야 한다.
- **부모는 지휘만 한다.** 부모가 직접 쓰거나 고치면 그 부분이 차례 처리 병목이 된다. 판단은 부모에게 남기되, 쓰는 일은 맥락이 분리된 담당이 동시에 한다.
- **실험은 같은 입력으로, 시간은 두 번 이상 잰다.** 같은 코드도 모델 배포 상태에 따라 run 시간이 5~10분씩 흔들렸다. 한 번 잰 시간 차이로 구조를 판단하면 엉뚱한 결론이 나온다.

아직 남은 것도 있다. 인력과 Activity 페이지는 여전히 단일 에이전트 결과보다 얇고, 원본 수백 건이 여러 run으로 나뉘어 들어올 때의 시간과 품질은 더 재 봐야 한다.
